## Critical

### C1 — WebSocket origin allowlist blocks the production domain

**File:** `apps/worker/src/live-gw-do.ts:126–130`

```ts
const isAllowedOrigin =
  !origin ||
  origin === 'http://localhost:3000' ||
  /^https:\/\/[a-z0-9-]+\.simply-fpl\.pages\.dev$/.test(origin);
```

The allowlist covers `localhost` and preview deployments (`*.simply-fpl.pages.dev`) but not `https://simplyfpl.com` or `https://www.simplyfpl.com`. When Cloudflare Pages serves the app on its custom domain, the browser sends `Origin: https://simplyfpl.com` on the WebSocket upgrade request; the DO returns 403. Live-rank WebSockets are broken for every production user.

**Fix:** add `origin === 'https://simplyfpl.com' || origin === 'https://www.simplyfpl.com'` to the check, or drive the list from an env var (`ALLOWED_ORIGINS`).

**Issue:** #387

### C2 — Frank on-demand quota check has a race condition (spend protection failure)

**File:** `apps/web/src/app/api/frank/ask/route.ts:122–135`

The count query and the Anthropic call are not atomic. Two concurrent requests from the same user where `used = 79` both read 79, both pass `< 80`, and both fire an Anthropic API call. Under load (or from two browser tabs), a user at quota limit can consume N × their hard cap of credits.

```ts
const { count: monthlyCount } = await supabase
  .from('frank_queries')
  .select('id', { count: 'exact', head: true })
  ...
// ← gap: another request arrives here, reads the same count
const message = await client.messages.create({ ... }); // both proceed
```

**Fix:** insert a placeholder row into `frank_queries` **before** calling Anthropic (using the admin client so RLS doesn't interfere), run the Anthropic call, then update that row with the response. The `INSERT` with the unique constraint prevents double-execution. Alternatively, use a Supabase DB function with `SELECT ... FOR UPDATE` to atomically increment a counter.

**Issue:** #388

### C3 — Stripe webhook: business handlers run before the idempotency record is written

**File:** `apps/web/src/app/api/stripe/webhook/route.ts:169–206`

`markProcessed(event.id)` is called on line 198 — after the `switch(event.type)` block (line 169). If Stripe delivers the same event to two parallel Edge Function invocations (fast retry, or duplicate delivery), both execute the handler before either writes to `stripe_events`. For `handleDisputeCreated` this also triggers a redundant `charges.retrieve()` Stripe API call. For `handleCheckoutCompleted` and `handleSubscriptionDeleted` the DB writes are idempotent, so no data corruption today, but this is one schema change away from a double-execution bug.

**Fix:** call `markProcessed` first; return 200 immediately on `duplicate`; only proceed to the business handler on `ok`.

```ts
const result = await markProcessed(event.id);
if (result === 'duplicate') return NextResponse.json({ received: true });
if (result === 'error') {
  return NextResponse.json({ error: 'Failed to record event' }, { status: 500 });
}
// now run the handler
```

**Issue:** #389

## High

### H1 — `getSession()` used instead of `getUser()` in analytics identity route

**File:** `apps/web/src/app/api/analytics/identity/route.ts:17`

```ts
const {
  data: { session },
} = await supabase.auth.getSession();
```

`getSession()` reads the JWT from the cookie without re-validating it against the Supabase auth server. A forged or replayed JWT passes. `getUser()` makes a network call to Supabase and validates the token. The impact here is limited (leaking a one-way hashed user ID for analytics), but it's the wrong pattern in a server route.

**Fix:** replace with `supabase.auth.getUser()` as every other route handler does.

**Issue:** #390

### H2 — Cohort KV lock is non-atomic (TOCTOU race)

**File:** `apps/worker/src/cohort/fetch-tier.ts:177–182`

```ts
async function acquireLock(...): Promise<boolean> {
  const existing = await env.FPL_CACHE.get(lockKey(gw, tier));
  if (existing) return false;
  await env.FPL_CACHE.put(lockKey(gw, tier), '1', { expirationTtl: 300 });
  return true;
}
```

KV has no atomic compare-and-set. Two concurrent cron invocations can both call `get(lockKey)`, both find `null`, and both proceed to `put`. Both then read the same `PartialAggregate`, independently merge their slices of FPL entries, and the second `writeAggregate` silently discards the first's work. The aggregate is under-counted and the cursor is corrupted.

**Fix:** Route cohort fetch coordination through a Durable Object (a single-instance lock holder), or promote the cohort scheduler itself to a DO alarm so only one invocation runs at a time.

**Issue:** #391

### H3 — `customer.subscription.updated` does not check subscription status

**File:** `apps/web/src/app/api/stripe/webhook/route.ts:87–110`

`handleSubscriptionUpdated` fires on any status transition — including `past_due`, `unpaid`, and `canceled` — but never inspects `subscription.status`. It only reads the price ID and sets the tier. Stripe fires `customer.subscription.updated` when a subscription is canceled via the API with `status: canceled` (distinct from `customer.subscription.deleted` which fires at end-of-period or immediate cancellation). A user who cancels mid-cycle through the billing portal can retain their paid tier until the next deletion event, but a customer who cancels via Stripe Dashboard (where Stripe sets status to `canceled` immediately) may retain access indefinitely if `deleted` is never fired.

**Fix:** add a status guard:

```ts
const allowed = ['active', 'trialing'];
if (!allowed.includes(subscription.status)) return;
```

**Issue:** #392

---

### H4 — `/snapshot/entry/:id` has no rate limiting

**File:** `apps/worker/src/index.ts:409–417`

Every other public route goes through `enforceRateLimit`. The snapshot route bypasses it entirely. On a KV cache miss, it fans out to the FPL API for bootstrap + entry + picks (up to 3 upstream calls per request). An attacker cycling through entry IDs can cause sustained, uncached upstream fan-out to FPL with no backpressure.

**Fix:** apply `enforceRateLimit(env, clientIp, PUBLIC_RATE_LIMIT)` before the snapshot handler, same as `/fpl/*`.

**Issue:** #393

## Medium

### M1 — Frank quota count uses the anon (RLS-bound) client

**File:** `apps/web/src/app/api/frank/ask/route.ts:122–128`

The count query runs through `supabase` (the SSR anon client), so the result depends on the RLS SELECT policy on `frank_queries`. If that policy is ever loosened or mis-applied, a user could see a lower count than reality and bypass the quota. The insert that enforces quota uses the admin client (line 228), creating an inconsistency.

**Fix:** use `getSupabaseAdminClient()` for the count query in the route handler, as the admin page does.

### M2 — Frank on-demand: identical questions make separate Anthropic calls

**File:** `apps/web/src/app/api/frank/ask/route.ts:210–216`

There is no deduplication of on-demand questions. Two different users (or the same user in two tabs) asking "Who should I captain this week?" both trigger full Anthropic calls with the same prompt. At scale this is the largest avoidable cost in the Frank feature.

**Fix:** compute `hash = SHA-256(question.toLowerCase() + ':' + weeklyGwId)`, check `FRANK_WEEKLY_CACHE.get('q:' + hash)`, and serve from cache on hit. Write the response with a TTL of 24 hours. The hash key space is small enough (~100 distinct popular questions per GW) that KV storage cost is negligible.

### M3 — Transfer data is never written to cohort aggregates

**File:** `apps/worker/src/cohort/fetch-tier.ts:234`

```ts
addTransfers(agg, null, null);
```

Both arguments are hard-coded `null`, so `transfersIn` and `transfersOut` maps remain empty forever. The cohort aggregate payload serialises these as empty arrays. The `PartialAggregate` type, the `serialiseAggregate` function, and the Supabase flush all carry the transfer fields as if they were populated.

**Fix:** either implement transfer tracking by passing real `transfers_in` / `transfers_out` element IDs from `picks.transfers` (requires fetching `/entry/:id/transfers/`), or remove the transfer fields from the aggregate schema and payload until the feature is built.

---

### M4 — Frank weekly re-runs Anthropic even if the current GW is already cached

**File:** `apps/worker/src/frank/weekly-cache.ts:99–151`

`runFrankWeekly` unconditionally calls `client.messages.create`. It does not check whether `frankWeeklyCacheKey(gwId)` already exists in KV before making the API call. The cron fires once per week (`0 6 * * 2`) so this is usually fine, but if the cron is manually triggered, a replay/test run, or the wrangler cron is duplicated, an extra Anthropic call is made and overwrites the existing advice with a potentially different response.

**Fix:** add an early-return guard:

```ts
const existing = await env.FRANK_WEEKLY_CACHE.get(frankWeeklyCacheKey(gwId));
if (existing) return;
```

### M5 — `?gw=` accepts arbitrary values and creates orphaned Durable Objects

**File:** `apps/worker/src/index.ts:369–383`

The only validation on `?gw=` is `/^\d+$/`. A request with `?gw=9999` creates a DO named `gw:9999`, which then starts alarm-polling FPL for a non-existent gameweek. Each unique value allocates a distinct DO instance. An attacker can create hundreds of orphaned DOs and associated FPL polling loops with no rate limit (the rate limit is applied only to the `/fpl/*` passthrough, not to `/live/ws`).

**Fix:** validate `gw` against a known range (1–38) or against the live gameweek ID from KV bootstrap.

## Low

### L1 — Admin client singleton silently falls back to placeholder key

**File:** `apps/web/src/lib/supabase-admin.ts:12–14`

```ts
const key = process.env['SUPABASE_SERVICE_ROLE_KEY'] || PLACEHOLDER_KEY;
```

If `SUPABASE_SERVICE_ROLE_KEY` is absent, the singleton is initialised with a placeholder. The singleton is never re-initialised in the same isolate lifetime, so later requests using the admin client silently fail with auth errors rather than failing fast with a startup crash. Use `requireEnv` (from `lib/env.ts`) to throw at startup.

### L3 — `/fpl/me/` in allowlist but always fails

**File:** `apps/worker/src/passthrough.ts:21`

The `/me/` FPL endpoint requires the user's session cookie to be forwarded. The worker does not forward cookies, so every proxied `/fpl/me/` call returns 401 from FPL. The route is dead weight in the allowlist.

### L4 — Frank question input has no content filter

**File:** `apps/web/src/app/api/frank/ask/route.ts:148`

Questions are capped at 500 characters but not checked for prompt-injection patterns (e.g., "Ignore previous instructions and…"). The risk is low (no system actions are taken based on the response) but worth a basic keyword blocklist before launch.

---

### L5 — Frank weekly: bootstrap context block changes per run, reducing prompt-cache hit rate

**File:** `apps/worker/src/frank/weekly-cache.ts:114–125`

The `contextJson` block (top-60 players, sorted by total_points) is placed in the system prompt with `cache_control: { type: 'ephemeral' }`. Anthropic caches the prefix only if it matches byte-for-byte. Anything that changes the bootstrap (new player news, transfer window updates) busts the cache. Since `runFrankWeekly` runs only once per week this is a single cache miss per run, not a per-request problem — acceptable but worth noting.

## Caching Opportunities

### CO1 — On-demand Frank question cache (largest AI credit saving)

See M2. Deduplicating the ~20 most popular questions per gameweek would cut on-demand Anthropic spend by an estimated 60–80% at scale.

### CO2 — Frank weekly: check GW cache before generating

See M4. One wasted Anthropic call per manual trigger or test run. Easy to guard.

### CO3 — `bootstrap-static-slim` client staleTime vs KV TTL alignment

**File:** `apps/worker/src/index.ts:89` — bootstrap KV TTL is 3600s. Client staleTime for the slim endpoint should match exactly. Confirm `staleTime: 60 * 60 * 1000` is set on every consumer of the slim bootstrap; a mismatch causes avoidable re-fetches from the worker.

### CO4 — Cohort aggregates: stale-while-revalidate window is narrow

**File:** `apps/worker/src/cohort/serve.ts:9`

```ts
const CACHE_CONTROL = 'public, max-age=60, stale-while-revalidate=300';
```

Cohort data is only updated on the scheduled cron (every 10–15 minutes during a live gameweek). The `max-age=60` causes CDN re-validation every minute for a resource that changes at most once per 10 minutes. Raising `max-age` to 300 and `stale-while-revalidate` to 600 would cut cohort aggregate CDN round-trips by ~5×.

### CO5 — Rate-limit KV keys use `Date.now()` in `checkRateLimit`

**File:** `apps/worker/src/index.ts:70`

```ts
const check = await checkRateLimit(env.FPL_CACHE, ..., Date.now());
```

Each rate-limit check writes a KV entry. Using the shared `FPL_CACHE` namespace for rate-limit keys means rate-limit writes contend with FPL data reads. A separate KV namespace (or a DO) for rate-limit state would improve isolation and give more accurate sliding-window semantics.
