## Tamagui extraction dead-end analysis (July 2026)

### What was attempted

Ref: #390, #49

#### Step 1 — rc.42 baseline with `disableExtraction: false`

Enabled `disableExtraction: false` + `outputCSS: './public/tamagui.css'` on Tamagui
`2.0.0-rc.42`. Result:

- Build succeeds (no SSR errors — the React 19 blockers from #49 are resolved)
- `[tamagui] built config, components, prompt (~963ms)` — plugin runs
- Bundle sizes: **identical** to the `disableExtraction: true` baseline
  - `/` first-load JS: 211 kB (baseline) vs 211 kB (extraction on) — no change
  - shared: 103 kB in both cases
- `public/tamagui.css`: 12,124 bytes — same as the design-tokens-only CSS from
  `generate-tamagui-css.mjs`, no per-component atomic CSS emitted

This confirms Pete's 2026-06-15 finding on #49.

#### Step 2 — Upstream check

Checked Tamagui npm releases. `2.0.0-rc.42` was the last RC; stable `2.4.0` shipped
2026-06-27. Commits between April and May 2026 that landed in `2.4.0` include:

- `fix(static): preserve imported component config during extraction` (2026-05-21)
- `fix(static): emit non-style props once and rename dynamic ones` (2026-05-04)
- `feat(compiler): auto-discovered tsconfig paths, improved dynamic eval and core component discovery` (2026-03-11)
- `feat(static): auto-optimize user-defined styled components behind enableDynamicEvaluation flag` (2026-02-27)

These looked directly relevant to our symptom (extractor finds configs but extracts nothing).

#### Step 3 — Upgrade to Tamagui 2.4.0

Updated all Tamagui package versions to `2.4.0` across `packages/ui`, `apps/web`,
`apps/mobile`. Three patches were ported to the new version:

1. `@tamagui/next-plugin@2.4.0.patch` — webpack instance fix (same as rc.42 patch;
   upstream PR tamagui/tamagui#4040 still not merged in 2.4.0)
2. `@tamagui/web@2.4.0.patch` — four runtime fixes (animation style flattening,
   `needsCssStyles` web-host check, `flattenStyle` in slot merging, `setupReactNative`
   false-match removal)
3. `tamagui-loader@2.4.0.patch` — CSS loader path fallback; `dist/esm/` ships
   `css.mjs` but the loader's try-chain only tries `css.cjs`, `css.esm`, `css.js` —
   the patch adds `css.mjs` as a final fallback

All three patches applied cleanly. `pnpm typecheck` passes across all 9 packages.

Added `enableDynamicEvaluation: true` (added in Feb 2026, specifically for

### Root cause

The Tamagui static extractor works by analysing **JSX at build time**. It can only
process code that the webpack compiler evaluates server-side. In this app:

- Every component that renders Tamagui primitives is marked `'use client'` (because
  they use `useState`, `useEffect`, React Query hooks, etc.)
- Pages are thin Server Component shells that render `<HomeChooser />`,
  `<DashboardView />`, etc., all of which are client components
- The extractor builds the config cache (it finds the component shapes), but then has
  no server-side JSX to analyse — all the actual `<DeltaChip />`, `<StatTile />`,
  `<XStack />` etc. usage is inside `'use client'` files, which the extractor skips

The extractor **cannot cross `'use client'` boundaries**. This is a fundamental
constraint of the static-analysis approach: if the component tree is dynamic
(client-side), the CSS rules can't be determined at build time.

### Acceptance criterion update

The original acceptance criteria in #49:

- ✅ `withTamagui` re-engaged — done (since June 2026)
- ✅ No RSC / SSR errors — confirmed on rc.42 and 2.4.0

- ❌ Bundle reduction ≥10 kB gzipped — not achievable yet

### Path forward

For extraction to produce a measurable bundle reduction, one of these is needed:

**Option A — Promote leaf components to Server Components.** Any Tamagui component
used only in static contexts (no hooks, no data) can be extracted. E.g. the `/brand`,
`/vs-livefpl`, `/login` page shells use layout components that could be server-only.
Even a handful of extractable components gives the extractor something to work with.
Measure impact per route before committing to a wider refactor.

**Option B — Migrate to `@opennextjs/cloudflare`.** Per the #49 comment from May
2026, the adapter change may alter the RSC/edge-runtime equation. This is uncertain
and should be evaluated alongside any future extraction attempt.

**Option C — Wait for RSC-aware extraction in Tamagui.** The team is aware of the
client-boundary limitation (it's an open design problem in Tamagui's extractor).
